[Apps](/docs/concepts/projects-and-apps) represent a specific platform build within a project. Each app has a platform (`apple`, `android`, `web`, `backend`) and an app-scoped `client_secret` API key for SDK use. Only native `apple`/`android` registration requires an immutable bundle identifier (`com.example.acme`) as metadata. Web/backend apps need none; SDK requests use the client key alone to identify the app. A web app additionally carries an editable `allowed_origins` list naming the browser origins its client key may send from.

**Locale demand.** Each user carries two locale signals captured by the SDK: their **wanted** language (e.g. `fr-FR` — `Locale.preferredLanguages.first` on Apple, `navigator.language` in the browser) and the **shown** locale (`Locale.current` on Apple, and in the browser the same `navigator.language`, since a page renders in whatever the browser asked for). The SDK also reports the languages the app ships (`Bundle.main.localizations` on Apple, the `supportedLanguages` option elsewhere), so the **localization gap** — demand for a language the app doesn't ship yet — is computed automatically: a language is flagged `shipped: false` when its base language isn't in the app's shipped set. The country breakdown works for every user today; the language breakdown fills in as users upgrade to the SDK that reports preferred language. Like user listings, locale demand respects the `data_mode` filter (`production` default, `development`, or `all`), so test installs don't skew which languages your real users want.
