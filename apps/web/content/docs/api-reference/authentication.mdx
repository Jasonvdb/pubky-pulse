title: Authentication
description: Auth endpoints — send verification code, verify code, whoami, and agent login.

Auth endpoints for email verification, user profiles, and API key management. All auth routes are prefixed with `/v1/auth`.

## Who can sign in

Only addresses whose domain appears in the server's `PULSE_ALLOWED_EMAIL_DOMAINS` allowlist can authenticate. Matching is exact and case-insensitive — with only `example.com` configured, `user@sub.example.com` is rejected. Every allowed user joins the one configured team, as `owner` if their address matches `PULSE_TEAM_OWNER_EMAIL` and as `member` otherwise. There is no invitation flow.

All three code-consuming routes (`/send-code`, `/verify-code`, `/agent-login`) check the domain **independently**, so a code created before a policy change cannot be redeemed after it.

Sessions are revalidated against the database on every request: a JWT stops working the moment its user, its email domain or its team membership becomes invalid, and an agent key stops working the moment its *creator* does. See [Authentication & Access Control](/docs/concepts/authentication).

## POST /v1/auth/send-code

Send a 6-digit verification code to an email address. Rate limited to 5 codes per email per hour. Codes expire after 10 minutes.

**Auth required:** No

The domain check runs first, before the rate-limit read, the code insert and the send. A disallowed address leaves no verification row, consumes no rate-limit slot and triggers no email.

```json
// Request
{
  "email": "user@example.com"
}

// Response (200)
{
  "message": "Verification code sent"
}

// Error: domain not configured (403)
{
  "error": "This email domain is not permitted to sign in"
}
```

The submitted address is never echoed back in the error or written to the logs.

## POST /v1/auth/verify-code

Verify the code and authenticate. Sets a JWT cookie (`token`, httpOnly, 10-year `maxAge` — sessions don't expire). If the email has no account, one is created automatically and attached to the configured team. No team is ever created here.

An allowed user whose membership is missing has it repaired on a successful sign-in. A disallowed address is rejected with `403` before the code is consumed, so the code stays unused.

**Auth required:** No

```json
// Request
{
  "email": "user@example.com",
  "code": "123456"
}

// Response (200 existing user, 201 new user)
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "name": "User",
    "created_at": "2024-01-01T00:00:00.000Z",
    "updated_at": "2024-01-01T00:00:00.000Z"
  },
  "teams": [
    {
      "id": "uuid",
      "name": "Example Team",
      "slug": "example-team",
      "role": "member",
      "default_agent_key": "pulse_agent_..."
    }
  ],
  "is_new_user": false
}
```

`teams` always holds exactly one entry: the configured team. `role` is `owner` only for `PULSE_TEAM_OWNER_EMAIL`.

`default_agent_key` is **this user's** oldest non-deleted agent key, never a colleague's. It is used by the MCP setup flow and omitted when the user has no agent key yet.

## POST /v1/auth/agent-login

Verify code and provision an agent API key in one step, for non-browser clients. Does not set a JWT cookie.

The same domain check as `/verify-code` applies, and is performed before the code is consumed. Since every user belongs to exactly one team, `team_id` can be omitted.

The key belongs to the person who authenticated: it carries their project ownership and nobody else's, and it stops working if their access is withdrawn.

**Auth required:** No

```json
// Request
{
  "email": "user@example.com",
  "code": "123456",
  "team_id": "uuid"  // optional — there is only one team
}

// Response (201)
{
  "api_key": "pulse_agent_abc123...",
  "team": {
    "id": "uuid",
    "name": "Example Team",
    "slug": "example-team"
  }
}

// Error: domain not configured (403)
{
  "error": "This email domain is not permitted to sign in"
}
```

A `team_id` that is not the caller's own membership returns `403`.

## POST /v1/auth/default-agent-key

Find or create the calling user's own default agent key. Used by the MCP setup flow so agents can bootstrap access without manually creating a key.

The lookup is scoped to `created_by = the current user`, so this never returns a colleague's agent secret. Find-or-create runs under a lock, so two concurrent calls — the dashboard opening MCP setup in two tabs, say — cannot both create a key.

**Auth required:** Yes (JWT only)

```json
// Request
{
  "team_id": "uuid"
}

// Response — existing key returned (200)
{
  "secret": "pulse_agent_abc123...",
  "created": false
}

// Response — new key created (201)
{
  "secret": "pulse_agent_xyz789...",
  "created": true
}
```

## POST /v1/auth/logout

Clear the JWT cookie.

**Auth required:** No

```json
// Response (200)
{
  "success": true
}
```

## GET /v1/auth/whoami

Return identity info for the current auth context. Works with both JWT and API key auth.

**Auth required:** Yes (JWT or API key)

```json
// Response — API key auth
{
  "type": "api_key",
  "key_type": "agent",
  "team": {
    "id": "uuid",
    "name": "Example Team",
    "slug": "example-team"
  },
  "permissions": ["events:read", "apps:read", "apps:write", "..."]
}

// Response — JWT auth
{
  "type": "user",
  "email": "user@example.com",
  "teams": [
    { "id": "uuid", "name": "Example Team", "slug": "example-team", "role": "member" }
  ]
}
```

`permissions` describes only what the *key* is allowed to attempt. A project write also requires the key's creator to own that project, which `whoami` does not report — read `access_level` from the [project response](/docs/api-reference/projects) instead.

## GET /v1/auth/keys

List the API keys the caller is entitled to see.

**Auth required:** Yes (JWT only)

Visibility is applied to the query, not to the response afterwards:

- **agent keys you created** — full metadata and `secret`;
- **client and import keys of apps in projects you own** — full metadata and `secret`;
- the **team owner** additionally sees metadata for every key in the team, with `secret: null` for any key they are not otherwise entitled to.

A `secret` you may not read is always `null` — never omitted, and never another key's value.

| Parameter | Type | Description |
|-----------|------|-------------|
| `team_id` | string | Optional. Filter to keys from a specific team. |

```json
// Response (200)
{
  "api_keys": [
    {
      "id": "uuid",
      "secret": "pulse_client_abc123...",
      "key_type": "client",
      "app_id": "uuid",
      "team_id": "uuid",
      "name": "iOS App Client Key",
      "created_by": "uuid",
      "created_by_email": "user@example.com",
      "permissions": ["events:write"],
      "created_at": "2024-01-01T00:00:00.000Z",
      "updated_at": "2024-01-01T00:00:00.000Z",
      "last_used_at": "2024-01-15T10:00:00.000Z",
      "expires_at": null,
      "app_name": "iOS App"
    },
    {
      "id": "uuid",
      "secret": null,
      "key_type": "agent",
      "app_id": null,
      "team_id": "uuid",
      "name": "A colleague's Agent Key",
      "created_by": "uuid",
      "created_by_email": "colleague@example.com",
      "permissions": ["events:read", "..."],
      "created_at": "2024-01-01T00:00:00.000Z",
      "updated_at": "2024-01-01T00:00:00.000Z",
      "last_used_at": null,
      "expires_at": null,
      "app_name": null
    }
  ]
}
```

The second entry is what the team owner sees for a key they may revoke but not read. Render `secret: null` as unavailable metadata, not as an empty credential.

## GET /v1/auth/keys/:id

Get a single API key by ID.

**Auth required:** Yes (JWT only)

Single-key visibility is exactly the list's, so knowing a key's UUID never reveals its secret. A key you may not see returns `404`, not `403` — a `403` would confirm it exists. A key you may see but not read comes back with `secret: null`.

```json
// Response (200)
{
  "api_key": {
    "id": "uuid",
    "secret": "pulse_agent_xyz9",
    "key_type": "agent",
    "app_id": null,
    "team_id": "uuid",
    "name": "Agent Key",
    "created_by": "uuid",
    "permissions": ["events:read", "apps:read", "apps:write", "..."],
    "created_at": "2024-01-01T00:00:00.000Z",
    "updated_at": "2024-01-01T00:00:00.000Z",
    "last_used_at": null,
    "expires_at": null
  }
}
```

## POST /v1/auth/keys

Create a new API key.

**Auth required:**

| Key type | Who may create it |
|---|---|
| `agent` | Any team member, for themselves. The key carries only that person's access. |
| `client` / `import` | A human who **owns the app's project**, with `apps:write` for a key caller. |

An **agent key** may create `import` keys only, only for an app in a project its creator owns, and only with `apps:write`. It cannot list, read, update or revoke keys — this create response is the one place it ever sees a secret. Client and import keys are rejected from every key-management route.

```json
// Request
{
  "name": "Production Agent Key",
  "key_type": "agent",          // "client", "agent", or "import"
  "team_id": "uuid",            // required for agent keys without app_id
  "app_id": "uuid",             // required for client keys
  "permissions": ["events:read", "apps:read"],  // optional, defaults applied per key type
  "expires_in_days": 90         // optional, key never expires if omitted
}

// Response (201)
{
  "api_key": {
    "id": "uuid",
    "secret": "pulse_agent_full_key...",
    "key_type": "agent",
    "app_id": null,
    "team_id": "uuid",
    "name": "Production Agent Key",
    "created_by": "uuid",
    "permissions": ["events:read", "apps:read"],
    "created_at": "2024-01-01T00:00:00.000Z",
    "updated_at": "2024-01-01T00:00:00.000Z",
    "last_used_at": null,
    "expires_at": "2024-04-01T00:00:00.000Z"
  }
}
```

### Permission defaults

If `permissions` is omitted, defaults are applied:

| Key type | Default permissions |
|----------|-------------------|
| Client | `["events:write", "users:write"]` |
| Agent | All agent permissions: `events:read`, `funnels:read`, `funnels:write`, `apps:read`, `apps:write`, `projects:read`, `projects:write`, `metrics:read`, `metrics:write`, `audit_logs:read`, `users:write`, `jobs:read`, `jobs:write`, `issues:read`, `issues:write`, `feedback:read`, `feedback:write`, `questionnaires:read`, `questionnaires:write` |
| Import | `["events:write", "users:write"]` |

Client and import keys share the same permissions (`events:write`, `users:write`). Import keys require an `app_id` and are used with the [bulk import endpoint](/docs/api-reference/import).

The `secret` in a create response is always the real value — this is the one response that carries a freshly minted credential.

## PATCH /v1/auth/keys/:id

Update an API key's name or permissions.

**Auth required:** Yes (JWT only) **and entitlement to the key** — you created it (agent keys), or you own the project of its app (client/import keys).

The team owner can *see* and *revoke* every key, but recovery authority is not an ownership claim: updating a key they are not entitled to returns `403`. An invisible key returns `404`.

```json
// Request
{
  "name": "Renamed Key",
  "permissions": ["events:read", "apps:read"]
}

// Response (200)
{
  "api_key": { ... }
}
```

## DELETE /v1/auth/keys/:id

Revoke (soft-delete) an API key.

**Auth required:** Yes (JWT only) and visibility of the key.

Revocation is the one action the team owner's recovery authority performs: they may revoke any key in the team without ever being able to read or edit it. Everyone else may revoke only keys they are entitled to. A key you cannot see returns `404`.

```json
// Response (200)
{
  "deleted": true
}
```
