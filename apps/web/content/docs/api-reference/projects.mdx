title: Projects
description: Endpoints for managing projects and their owner lists — create, list, get, update, delete, and add or remove project owners.

Create, list, get, update, and delete projects, and manage who owns them. Projects group related apps across platforms (e.g., a "MyApp" project containing iOS, Android, and web apps).

## Reads and writes

Every member of the team can **read** every active project. **Writing** to a project requires being one of its owners.

Every project response therefore carries two access fields:

| Field | Type | Description |
|---|---|---|
| `owners` | array | `{ user_id, name, email }` for each owner. Visible to every team member. |
| `access_level` | string | `owner` or `viewer` — the caller's own effective access to this project. |

For an agent key, `access_level` describes the human who created the key, because that is whose ownership authorizes its writes. Use this field rather than inferring authority from a team role. A write attempted as a `viewer` returns `403 Requires project ownership` and changes nothing.

`client_secret` on a nested app is `null` unless the caller owns the project — including for the team owner, who does not gain secrets by being the team owner. See [Authentication & Access Control](/docs/concepts/authentication).

## GET /v1/projects

List all projects in the team. Every team member sees every project, owned or not.

**Auth required:** Yes (`projects:read` permission or JWT)

| Parameter | Type | Description |
|-----------|------|-------------|
| `team_id` | string | Optional. Filter to a specific team. |

```json
// Response (200)
{
  "projects": [
    {
      "id": "uuid",
      "team_id": "uuid",
      "name": "My App",
      "slug": "my-app",
      "color": "#22c55e",
      "retention_days_events": null,
      "retention_days_metrics": null,
      "retention_days_funnels": null,
      "effective_retention_days_events": 120,
      "effective_retention_days_metrics": 365,

      "effective_issue_alert_frequency": "daily",
```

## POST /v1/projects

Create a new project. **Any team member may create one**, and the creator becomes its first owner — the project row and the first owner row are inserted in a single transaction, so a project is never left ownerless.

**Auth required:** Yes (`projects:write` permission or JWT)

For an agent key the first owner is the key's creator, never the key. Client and import keys have no human actor and receive `403`.

```json
// Request
{
  "team_id": "uuid",
  "name": "My App",
  "slug": "my-app",
  "retention_days_events": 90
}

// Response (201)
{
  "id": "uuid",
  "team_id": "uuid",
  "name": "My App",
  "slug": "my-app",
  "color": "#22c55e",
  "retention_days_events": 90,
  "retention_days_metrics": null,
  "retention_days_funnels": null,
  "effective_retention_days_events": 90,
  "effective_retention_days_metrics": 365,
  "effective_retention_days_funnels": 365,
  "owners": [
    { "user_id": "uuid", "name": "Creator", "email": "creator@example.com" }
  ],
  "access_level": "owner",
  "created_at": "2024-01-01T00:00:00.000Z"
}
```

A display color is auto-assigned on creation (picked from a palette of unused colors within the team). Use PATCH to override it. The request body does not accept `color`.

### Field reference

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `team_id` | string | Yes | The team this project belongs to. |
| `name` | string | Yes | Display name. |
| `slug` | string | Yes | URL-friendly identifier. Must match `^[a-z0-9-]+$`. Unique within a team. |
| `retention_days_events` | integer | No | Days to retain events. Default: 120. |
| `retention_days_metrics` | integer | No | Days to retain metric events. Default: 365. |
| `retention_days_funnels` | integer | No | Days to retain funnel events. Default: 365. |

Slug reuse: if a soft-deleted project exists with the same slug in the same team, it is hard-deleted to free the slug.

Returns `409` if an active project with the same slug already exists.

## PATCH /v1/projects/:id

Update a project's name, color, or data retention policies.

**Auth required:** Yes (`projects:write` permission or JWT) **and project ownership.** A viewer receives `403`.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | No | New display name. |
| `color` | string | No | Display color as `#RRGGBB` hex. Auto-assigned on creation; override to customize. |
| `retention_days_events` | integer or null | No | Days to retain events. `null` resets to default (120). |
| `retention_days_metrics` | integer or null | No | Days to retain metric events. `null` resets to default (365). |
| `retention_days_funnels` | integer or null | No | Days to retain funnel events. `null` resets to default (365). |
| `attachment_user_quota_bytes` | integer or null | No | Per-user attachment storage quota in bytes. `null` resets to default (250 MB). |
| `attachment_project_quota_bytes` | integer or null | No | Project-wide attachment storage quota in bytes. `null` resets to default (5 GB). |
| `issue_alert_frequency` | string or null | No | Issue notification cadence: `none`, `hourly`, `6_hourly`, `daily`, or `weekly`. `null` resets to default (`daily`). |

At least one field must be provided.

```json
// Request
{
  "name": "Renamed Project",
  "retention_days_events": 60
}

// Response (200)
{
  "id": "uuid",
  "team_id": "uuid",
  "name": "Renamed Project",
  "slug": "my-app",
  "color": "#22c55e",
  "retention_days_events": 60,
  "retention_days_metrics": null,
  "retention_days_funnels": null,
  "effective_retention_days_events": 60,
  "effective_retention_days_metrics": 365,
  "effective_retention_days_funnels": 365,
  "owners": [
    { "user_id": "uuid", "name": "Owner", "email": "owner@example.com" }
  ],
  "access_level": "owner",
  "created_at": "2024-01-01T00:00:00.000Z"
}
```

## DELETE /v1/projects/:id

Soft-delete a project and cascade to its apps, API keys, metric definitions, and funnel definitions.

**Auth required:** Yes (JWT only — agent keys receive `403`) **and project ownership.**

One recovery exception: the team owner may delete a project that has **no owners at all**, so an orphaned project can still be cleaned up. Team ownership is not a general delete bypass — for a project that still has owners, the team owner must add themselves as an owner first.

```json
// Response (200)
{
  "deleted": true
}
```

## Project Owners

A project's owners are equal peers: any of them may add or remove any other, including themselves, as long as one owner remains. Two rules sit on top.

**Owner-list changes are human-only.** An agent key inherits its creator's project access for ordinary writes but can never change who holds that access, so all three routes below reject agent, client and import keys with `403`.

**The team owner has recovery authority here** even without owning the project, so an ownerless project can be re-owned. That authority is scoped to this list and confers no ordinary project write.

All three routes return the same body: the full owner list plus the caller's resulting `access_level`.

### GET /v1/projects/:projectId/owners

Read a project's owners. Every team member may read it — that is how a viewer discovers who can act on the project.

**Auth required:** Yes (`projects:read` permission or JWT)

```json
// Response (200)
{
  "owners": [
    { "user_id": "uuid", "name": "Owner", "email": "owner@example.com" },
    { "user_id": "uuid", "name": "Co-owner", "email": "co-owner@example.com" }
  ],
  "access_level": "owner"
}
```

### PUT /v1/projects/:projectId/owners/:userId

Add an existing team member as an owner. **Idempotent** — re-adding a current owner is a successful no-op, so a retried request never turns into an error the client has to interpret.

**Auth required:** Yes (JWT only) **and project ownership**, or team-owner recovery.

No request body. Returns `404 User not found in this team` when `:userId` is not on the roster: there is no outside-user invitation path, and a `404` here keeps the endpoint from being used to probe for user IDs.

```json
// Response (200)
{
  "owners": [
    { "user_id": "uuid", "name": "Owner", "email": "owner@example.com" },
    { "user_id": "uuid", "name": "New Owner", "email": "new-owner@example.com" }
  ],
  "access_level": "owner"
}
```

The new owner's existing sessions and agent keys gain write access on their **next request**. Nothing has to be re-issued.

### DELETE /v1/projects/:projectId/owners/:userId

Remove an owner, including yourself.

**Auth required:** Yes (JWT only) **and project ownership**, or team-owner recovery.

| Status | Meaning |
|---|---|
| `200` | Removed. The response carries the remaining owners and your resulting `access_level` — which is `viewer` if you removed yourself. |
| `404` | That user is not an owner of this project. |
| `409` | A project must keep at least one owner. Nothing was changed. |

Counting and deleting happen together under a database lock, so two concurrent removals cannot both succeed and leave the project with zero owners.

```json
// Response (200)
{
  "owners": [
    { "user_id": "uuid", "name": "Owner", "email": "owner@example.com" }
  ],
  "access_level": "viewer"
}
```

The removed owner's existing sessions and agent keys lose write access on their next request; reads keep working.

Owner additions and removals are recorded in the [team audit log](/docs/api-reference/teams) as `project_owner` entries.
