---
title: Notifications
description: Multi-channel notification system — per-user inbox and email fan-out from a single producer call.
---

Notifications are the unified path for telling users something happened — a new feedback item arrived, an issue digest is ready, a manual job they triggered finished. Producers (the issue-scan job, feedback ingest, manual job runs) write a single record; the dispatcher fans it out across whichever channels each user has enabled.

## Two Primitives

The system is backed by two tables. Keeping them separate means a failed email retry doesn't touch the inbox row, and "did the email actually send?" is answerable without grepping a status grab-bag.

| Table | Purpose |
|-------|---------|
| `notifications` | Per-user inbox row. One per recipient, written synchronously on enqueue. Carries the pre-rendered `title`, `body`, optional deep `link`, structured `data`, `read_at`, `deleted_at`. |
| `notification_deliveries` | Per-channel attempt log. One row per enabled `(notification, channel)`. Status moves `pending → sent | failed | skipped`. When `in_app` is enabled, its delivery marker is created and marked `sent` synchronously alongside the unconditional inbox insert. |

## Channels

Notifications fan out across **channels**. The current set is `in_app` and `email`; adding Telegram, Slack, or webhook channels means dropping in a new `ChannelAdapter` and extending `NOTIFICATION_CHANNELS` — no producer change.

| Channel | Description |
|---------|-------------|
| `in_app` | Internal delivery marker for the inbox at `/dashboard/notifications`, with an unread badge on the user-menu avatar (polled every 30s). The inbox row itself is always written synchronously, independent of the stored `in_app` preference. |
| `email` | HTML email via Resend (or console logger in dev). Per-type formatters (`sendIssueDigest`, `sendJobAlert`) plus a generic fallback. |

## Notification Types

Each notification has a `type` that determines its formatters and declared delivery channels.

| Type | Trigger | Channels | Default On |
|------|---------|----------|------------|
| `issue.new` | Fires from the `issue_scan` job at the end of every run when one or more **production** issues were created or regressed. One notification per team per scan, summarizing all of that run's new + regressed issues — bypasses the per-project digest cadence so it lands in close to real time. Dev-build crashes are excluded. | `in_app`, `email` | `in_app` (email off by default) |
| `issue.digest` | Per-project periodic digest of new and regressed issues, sent by the `issue_notify` job at the project's configured frequency. | `in_app`, `email` | `email` only |
| `feedback.new` | A user submitted feedback in one of the team's apps. | `in_app`, `email` | Both |
| `questionnaire.response_new` | A user submitted a questionnaire response in one of the team's apps. Defaults skew to in-app only because responses can be high-volume — email is opt-in. | `in_app`, `email` | `in_app` only (email off by default) |
| `job.completed` | A manual job run triggered with `notify: true` finished — only the triggering user is notified, never the whole team. | `in_app`, `email` | Both |

Adding a new type is three steps: append to `NOTIFICATION_TYPES`, add an entry to `NOTIFICATION_TYPE_META` with default channel state, and wire a producer call site to `dispatcher.enqueue(...)`.

## Per-User Preferences

Channel preferences live under `users.preferences.notifications.types` as a sparse override map: missing entries fall back to the type's defaults from `NOTIFICATION_TYPE_META`. Read and update via the standard user-prefs endpoints:

- `GET /v1/auth/me` returns the merged preferences blob.
- `PATCH /v1/auth/me` merges preference subtrees, including notification types and sibling channel overrides, so updating email does not discard an existing `in_app` value.

The dashboard's profile page at `/dashboard/profile/notifications` exposes only the email preference for each email-capable type and PATCHes that override. Existing `in_app` values remain stored for compatibility, but the dashboard does not expose them as preferences. An eligible recipient's inbox row is always created, regardless of either channel preference.

## Per-Project Alert Frequency vs Per-User Email

Two knobs cooperate:

- **Per-project `issue_alert_frequency`** (`none`, `hourly`, `6_hourly`, `daily`, `weekly`) is the **rate-limit / batching policy** — how often the `issue_notify` job assembles a digest for that project. It applies to all team members.
- **Per-user email toggles** decide whether the digest is also delivered by email. Dashboard inbox rows are always created.

A project on `daily` digests with three eligible team members creates an inbox notification for each member at the same hour. Email delivery follows each member's preference.

## System-Job Alerts Stay Direct

System job failures (`db_pruning`, `partition_creation`, `attachment_cleanup`, `app_version_sync`, etc.) are a **server-owner concern**, not a team-member concern. They keep going to `SYSTEM_JOBS_ALERT_EMAIL` via the direct email path and never enter the dispatcher or the inbox. There's intentionally no `system.alert` notification type.

## Transactional Email Stays Direct Too

One flow bypasses the dispatcher because the recipient may not yet have a `users` row: **verification codes**, sent via `EmailService.sendVerificationCode` straight from the `/v1/auth/send-code` route — and only after the address has passed the configured-domain check, so a disallowed address never triggers an email.

It reaches the email channel directly and is never written to a notifications inbox.

## Background Jobs

Two jobs back the system:

- `notification_deliver` — one job per `pending` row in `notification_deliveries`. The handler loads the row, runs the matching channel adapter, and updates the delivery's status. See [Background Jobs](/docs/concepts/background-jobs).
- `notification_cleanup` — daily at 6am UTC. Soft-deletes read notifications older than 30 days, hard-deletes soft-deleted notifications older than 90 days.

## Permissions

Notifications are **user-scoped, not team-scoped**. The REST routes accept JWT cookies only — agent API keys receive 403. There is intentionally **no MCP tool surface** for notifications: an agent has no inbox.
