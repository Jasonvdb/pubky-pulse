title: Projects & Apps
description: Organize your tracking with projects (cross-platform products) and apps (platform-specific builds).

Pubky Pulse uses a two-level hierarchy to organize your tracking: **projects** group related apps by product, and **apps** represent individual platform-specific builds.

## Projects

A project represents a product or service. If you ship a mobile app called "Acme" on iOS and Android with a web dashboard, all three would live under a single "Acme" project.

Projects are team-scoped and identified by a unique slug. They provide a shared namespace for:

- [Metric definitions](/docs/concepts/metrics) -- performance tracking is defined per-project
- [Funnel definitions](/docs/concepts/funnels) -- conversion funnels span apps within a project
- [Issue alerting](/docs/concepts/issues) -- per-project `issue_alert_frequency` (`none`, `hourly`, `6_hourly`, `daily` (default), `weekly`) controls the digest cadence only; instant `issue.new` fan-out fires every scan regardless
- [Attachment quotas](/docs/concepts/attachments) -- per-user and project-wide byte ceilings
- Apps -- the platform-specific builds that send events

Each project also has a required `#RRGGBB` hex **color** used throughout the dashboard to distinguish projects at a glance. If you omit the color on creation, the server auto-picks one from a 20-entry palette, avoiding colors already in use by other non-deleted projects in the same team. You can change the color any time via `PATCH /v1/projects/:id` or the MCP `update-project` tool.

Projects are managed through the dashboard, [MCP](/docs/mcp/projects), or the [API](/docs/api-reference/projects).

### Ownership

A project is the unit of write access. Every team member can **read** every project in the team; **changing** one requires being one of its owners.

- A project has one or more **equal owners**. There is no permanent creator role: whoever creates the project becomes its first owner, and from then on any owner can add or remove any other, including themselves.
- Owners are chosen from the existing team roster. There is no way to invite someone from outside the configured email domains.
- The **last owner can never be removed** — the attempt returns `409` and changes nothing.
- The **team owner** can repair any project's owner list, so an ownerless project can be recovered. That is recovery authority only: to make an ordinary change they must add themselves as an owner first.
- An **agent key** inherits the project access of the person who created it, re-read on every request. Adding or removing that person from a project changes what their key can do on its very next call, with no key re-issued.

Every project response carries `owners` and an `access_level` of `owner` or `viewer` for the caller, and the dashboard hides or disables write controls for a `viewer`. The server is authoritative — a stale page that attempts a forbidden write gets `403`. Non-owners keep full read access and can still comment on issues, feedback and questionnaire responses.

Ownership covers project settings and deletion, apps, metric and funnel definitions, issue triage and merging, feedback triage and deletion, questionnaires and responses, attachment deletion, project jobs, and client/import key management. See [Authentication & Access Control](/docs/concepts/authentication) for the full policy.

### Data Retention

Each project has configurable data retention policies that control how long event data is kept:

| Data type | Default retention | Description |
|-----------|-------------------|-------------|
| Events | 120 days | Raw log events from SDKs |
| Metrics | 365 days | Structured metric events |
| Funnels | 365 days | Funnel conversion events |

A daily background job deletes events older than the retention period. Set retention per-project via the dashboard, the `update-project` MCP tool, or the API. Set a value to `null` to use the system default.

Retention values must be between 1 and 3,650 days (approximately 10 years). Metric and funnel *definitions* are not affected by retention -- only the underlying event data is deleted.

## Apps

An app represents a single platform-specific build within a project. Each app has a platform, an optional bundle ID, and its own client API key for event ingestion.

### Platforms

Every app has a broad `platform` that categorizes what kind of build it is:

| Platform | Description | Bundle ID Required |
|---|---|---|
| `apple` | iOS, iPadOS, or macOS app | Yes |
| `android` | Android app | Yes |
| `web` | Web application | Yes |
| `backend` | Server-side application | No |

### Environments

While an app has a single platform, the events it sends carry a more specific `environment` field that records the exact runtime:

| Environment | Description |
|---|---|
| `ios` | iPhone |
| `ipados` | iPad |
| `macos` | Mac (native macOS or Mac Catalyst) |
| `watchos` | Apple Watch |
| `android` | Android device |
| `web` | Web browser |
| `backend` | Server process |

This distinction allows a single "apple" platform app to receive events from iOS, iPadOS, and macOS environments, which the SDKs detect automatically.

### Platform-to-Environment Mapping

Each platform allows a specific set of environments:

| Platform | Allowed Environments |
|---|---|
| `apple` | `ios`, `ipados`, `macos`, `watchos` |
| `android` | `android` |
| `web` | `web` |
| `backend` | `backend` |

## Bundle ID

Apps with a platform other than `backend` require a `bundle_id`. The ingest endpoint validates that the `bundle_id` in each request matches the app's registered bundle ID on every ingestion request.

What that string looks like follows the platform:

| Platform | Identifier | Example |
|---|---|---|
| `apple` | Reverse-DNS bundle identifier | `com.example.acme` |
| `android` | Application ID | `com.example.acme` |
| `web` | Site identifier — the site's host reads best | `app.acme.com` |
| `backend` | None | -- |

A web app's identifier is a name, not an address: it is not parsed as a URL, no scheme or path belongs in it, and it is not what authorises the browser to send. That is [allowed origins](#allowed-origins), below. Keep it stable — it is the value you pass as `bundleId` in `Pulse.configure()`.

Backend-platform apps have no bundle ID, and the ingest route skips this validation for them.

Bundle IDs are **immutable after creation**. The update endpoint accepts a `name` change and, for web apps, an `allowed_origins` change — never a bundle ID. If you need to change one, delete the app and create a new one.

## Allowed Origins

A `web` app carries `allowed_origins`: the list of browser origins its client key may send from. It is empty by default, editable at any time, and meaningful only on the `web` platform — setting it on an `apple`, `android`, or `backend` app is rejected with a `400`.

It exists because a web app's client key is public. It ships inside the page, so anyone can read it out of the network tab. The origin list is what scopes that key to the sites you actually own:

- **Ingest enforcement.** When a request for a web app carries an `Origin` header, that origin must be on the list or the request is refused with `403`. Requests with no `Origin` — native SDKs, backend SDKs, `curl` — pass untouched; none of them can forge a browser origin, and refusing them would break the platforms the list has nothing to say about.
- **CORS.** Registered origins are allowed automatically, so adding a site is an API or dashboard change rather than a server redeploy. `CORS_ORIGINS` stays what it always was: the dashboard's own origin.
- **An empty list means no browser can send.** A newly created web app with no origins refuses every request a browser makes. Add the site's origins — including the dev server's, `http://localhost:5173` or whatever port you use — before wiring up the SDK.

Each entry is a full origin and nothing else: scheme, host, and an optional port, with no path, no query string, and no trailing slash. That is exactly the shape of the `Origin` header a browser sends, so the comparison is a string equality rather than a guess about what a pattern meant.

```json
{
  "allowed_origins": [
    "https://app.acme.com",
    "https://staging.acme.com",
    "http://localhost:5173"
  ]
}
```

On write, entries are normalised — scheme and host lowercased, a default port dropped (`https://acme.com:443` becomes `https://acme.com`), duplicates collapsed — and anything that is not a bare `http`/`https` origin is rejected with a `400` naming the offending value. Wildcards are not supported; list each host. At most 50 entries per app.

Updating the list **replaces** it, so send the origins you want to keep alongside the new one. Changes take effect on ingest immediately and on CORS within a minute (the union of every web app's origins is cached briefly). Edit it from the app's card in the dashboard, `PATCH /v1/apps/:id`, or the `update-app` MCP tool.

## Auto-Created Client Key

When you create an app, Pubky Pulse automatically generates a client API key (`pulse_client_` prefix) as a row in the `api_keys` table, scoped to that app. The key is returned in the app creation response so you can configure your SDK immediately, and remains viewable from the **API Keys** page in the dashboard by anyone who owns the app's project.

A client secret is a project credential, so it is shown only to that project's owners. Everyone else — including the team owner — receives `client_secret: null` on app and project responses. A `null` means "you may not see this", not "there is no key".

## Latest App Version

Each app response includes two fields tracking the current public release: `latest_app_version` and `latest_app_version_updated_at`. The version is computed from the highest `app_version` seen in the app's last 90 days of production events — the same path for web, backend and mobile apps. These power the green/amber version badges shown in events, users, and issues across the dashboard and MCP. See [Latest Version Detection](/docs/concepts/latest-version-detection) for how it's resolved and refreshed.

## Typical Setup

A common configuration for a cross-platform product:

| Project | App | Platform | Bundle ID |
|---|---|---|---|
| Acme | Acme iOS | apple | `com.example.acme` |
| Acme | Acme Android | android | `com.example.acme` |
| Acme | Acme Web | web | `app.acme.com` |
| Acme | Acme API | backend | -- |

All four apps share the same project, so metric definitions, funnel definitions, and cross-platform analytics are unified under "Acme." Only the web app carries allowed origins; the other three send no `Origin` header.

For managing projects and apps, see the [MCP projects guide](/docs/mcp/projects), the [MCP apps guide](/docs/mcp/apps), or the [API reference](/docs/api-reference/projects).
