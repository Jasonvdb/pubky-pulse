Pubky Pulse is designed to be set up by your coding agent. There are four steps:

1. Run or access a Pubky Pulse instance
2. Sign in to the dashboard
3. Add the MCP server to your client
4. Tell your agent to create a project and an app, then integrate an SDK

## 1. Run or access an instance

Pubky Pulse is self-hosted, so the first thing you need is an instance to talk to.

- **Self-hosted server** — the path for everyone outside Pubky. A single VPS runs the API, the dashboard, and PostgreSQL. See the [Self-Hosting Quickstart](/docs/getting-started/self-hosting), or the [full Self-Hosting guide](/docs/self-hosting) for nginx, SSL, and firewall configuration.
- **Local development stack** — clone the repo and run it on your machine. Requires Node.js 20+, PostgreSQL 15+, and pnpm.

  ```bash
  pnpm install
  createdb pubky_pulse
  cp .env.example .env   # then set the four required PULSE_* identity variables
  pnpm db:migrate
  pnpm dev:seed     # sample team, project (with an owner), app, and API keys
  pnpm dev:server   # API on http://localhost:4000
  pnpm dev:web      # dashboard on http://localhost:3000
  ```

  Run `pnpm dev:server` and `pnpm dev:web` in separate terminals. The seed data is for development only — its API keys are committed to the repository and publicly known.
- **Pubky's instance** — Pubky runs its own instance at pulse.pubky.org for Pubky's apps. It is not an open sign-up service; see [Hosted instance](/docs/getting-started/hosted).

## 2. Sign in

Open the dashboard in a browser — `http://localhost:3000` for a local development stack, or whatever hostname you deployed the dashboard to. Enter your email and you'll receive a 6-digit verification code; enter it to sign in. No password needed, and your account is created automatically on first verification.

Sign-in is restricted to the email domains the instance was configured with (`PULSE_ALLOWED_EMAIL_DOMAINS`). An address outside them is refused with a `403` and no code is sent at all. Everyone who signs in joins the same single team and can read every project in it; changing a project needs to be one of its owners.

If no `RESEND_API_KEY` is configured, the verification code is printed to the API server console instead of being emailed.

Signing in also creates a default agent key (`pulse_agent_*`) that belongs to **you** — that is the credential your MCP client uses. It carries your project access and is visible only to you; colleagues get their own. You can create more keys later from the **API Keys** page.

## 3. Add the MCP server to your client

The [MCP endpoint](/docs/mcp/setup) is the agent interface: one HTTP URL gives your agent 62 tools, with nothing to install and no updates to keep on top of.

| Instance | MCP endpoint |
|----------|--------------|
| Pubky's instance (placeholder — substitute your own host) | `https://api.pulse.pubky.org/mcp` |
| Self-hosted | `https://api.yourdomain.com/mcp` |
| Local development | `http://localhost:4000/mcp` |

For Claude Code, the whole setup is one command:

```bash
claude mcp add --transport http --scope user pubky-pulse https://api.pulse.pubky.org/mcp \
  --header "Authorization: Bearer pulse_agent_YOUR_KEY_HERE"
```

Any supported MCP client works (Claude Code, Codex, OpenCode, Cursor, VS Code, Claude Desktop, Windsurf, Zed, JetBrains, Cline, Roo Code). The [MCP setup guide](/docs/mcp/setup) leads with the fastest safe method for each one and includes project-level or extension-specific fallbacks where available.

Verify the connection by asking your agent to call the `whoami` tool. It should return your key type, team, and permissions.

For CI/CD pipelines and shell scripts that can't speak MCP, the [REST API](/docs/api-reference) covers the same operations with the same `pulse_agent_` keys.

## 4. Tell your agent to set up Pubky Pulse

With the endpoint configured, give your coding agent a prompt like this:

```
Set up Pubky Pulse in this project. Use the Pubky Pulse MCP tools to create a
project and an app, then instrument the code with the SDK for this platform.
```

Supported clients read the `pubky-pulse://guide` resource automatically on connection, so your agent already knows the concepts, resource hierarchy, and conventions — it takes it from there: `create-project`, `create-app`, then installing the SDK and wiring up event tracking.

| SDK | Platforms | Docs |
|-----|-----------|------|
| Web | Browser apps | [/docs/sdks/web](/docs/sdks/web) |
| Node.js | Any Node.js backend | [/docs/sdks/node](/docs/sdks/node) |
| Swift | iOS, iPadOS, macOS, watchOS | [/docs/sdks/swift](/docs/sdks/swift) |
| Android | Android (Kotlin / Compose) | [/docs/sdks/android](/docs/sdks/android) |

**Tip:** Add this line to your project's `CLAUDE.md`, `AGENTS.md`, or whatever default instructions file your coding agent uses:

```markdown
### Pubky Pulse
Use the Pubky Pulse MCP tools for any analytics work — read the `pubky-pulse://guide`
resource first, and see https://pulse.pubky.org/docs/sdks for SDK integration.
```

Every future session then knows Pubky Pulse is integrated and picks up the right context automatically — including the full tool surface, funnel design rules, and lifecycle metric patterns.

## Doing it by hand

Prefer to click through the dashboard? Steps 1 and 2 are the same; instead of step 4:

### Create a project

In the dashboard sidebar, go to **Projects** and click **Create Project**. A project groups related apps across platforms (e.g., a web app, a backend service, and a mobile app under one project).

### Create an app

From your project's detail page, click **Create App**. Choose the platform that matches your target:

| Platform | Use for |
|----------|---------|
| Apple | iOS, iPadOS, macOS, watchOS apps |
| Android | Android apps |
| Web | Browser-based apps |
| Backend | API servers, workers, serverless functions |

For Apple, Android, and Web platforms, provide a **bundle ID**. On Apple and Android that's the reverse-DNS identifier (`com.example.myapp`); on Web it's the site identifier, and the site's host reads best (`app.example.com`). Backend apps don't need one.

A **Web** app also asks for **allowed origins** — the browser origins the SDK may send from, one per line, including your dev server (`http://localhost:5173`). A web app's client key ships inside the page, so this list is what scopes it to sites you own; leave it empty and the browser gets a `403`. You can edit it any time from the app's card. See [Allowed Origins](/docs/concepts/projects-and-apps#allowed-origins).

When you create the app, a client API key (`pulse_client_...`) is generated automatically. **Copy this key** — you'll need it to configure the SDK.

### Configure the SDK

Follow the installation page for your platform: [Web](/docs/sdks/web/installation), [Node.js](/docs/sdks/node/installation), [Swift](/docs/sdks/swift/installation), or [Android](/docs/sdks/android/installation). Each SDK is configured with two values: the client key you just copied and the ingest endpoint of your instance (`https://ingest.yourdomain.com`, or `http://localhost:4000` in local development).
