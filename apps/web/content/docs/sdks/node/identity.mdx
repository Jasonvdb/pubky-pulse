The Node.js SDK provides `Pulse.withUser()` to associate events with a specific user. This is the primary mechanism for per-user analytics, funnel tracking, and session tracing.

## withUser

`Pulse.withUser(userId)` returns a `ScopedPulse` instance. Every event emitted through this instance includes the given `user_id`:

```typescript
const pulse = Pulse.withUser("user_42");
pulse.info("Profile updated");
pulse.warn("Rate limit approaching");
pulse.step("onboarding-complete");
```

The returned `ScopedPulse` has the same API as `Pulse` -- `info()`, `debug()`, `warn()`, `error()`, `step()`, `startOperation()`, `recordMetric()`, and `setUserProperties()`. It can be further narrowed with `.withSession(sessionId)` for session scoping.

## Middleware Pattern

In HTTP servers, create a scoped instance per request based on the authenticated user. This is the recommended approach for associating backend events with users.

### Express

```typescript
import express from "express";
import { Pulse, type ScopedPulse } from "@synonymdev/pubky-pulse-node";

// Extend the Request type
declare global {
  namespace Express {
    interface Request {
      pulse: typeof Pulse | ScopedPulse;
    }
  }
}

const app = express();

app.use((req, res, next) => {
  req.pulse = req.auth?.userId
    ? Pulse.withUser(req.auth.userId)
    : Pulse;
  next();
});

app.get("/api/profile", (req, res) => {
  req.pulse.info("Viewed profile");
  res.json(req.user);
});

app.post("/api/settings", (req, res) => {
  req.pulse.info("Updated settings", { theme: req.body.theme });
  res.json({ ok: true });
});
```

### Fastify

```typescript
import Fastify from "fastify";
import { Pulse } from "@synonymdev/pubky-pulse-node";

const app = Fastify();

app.decorateRequest("pulse", null);

app.addHook("onRequest", async (request) => {
  request.pulse = request.user?.id
    ? Pulse.withUser(request.user.id)
    : Pulse;
});

app.get("/api/orders", async (request, reply) => {
  request.pulse.info("Listing orders");
  const orders = await getOrders(request.user.id);
  return orders;
});
```

## withSession

By default, a Node SDK process generates one session ID in `Pulse.configure()` and stamps every event with it. That works for a single long-running worker, but it isn't useful for a web server that handles many clients — all backend events end up in one giant session that doesn't line up with any client session.

`Pulse.withSession(sessionId)` returns a `ScopedPulse` that overrides the session ID for every event it emits:

```typescript
const pulse = Pulse.withSession("client-session-abc123");
pulse.info("Processed request");
```

This is most commonly paired with `withUser` to scope a full request handler:

```typescript
const pulse = Pulse.withSession(clientSessionId).withUser(userId);
pulse.info("Order created", { orderId });
```

The scopes chain in either order — `Pulse.withUser(uid).withSession(sid)` produces the same result.

`sessionId` should be a UUID string (the Swift SDK's `Pulse.sessionId` already is). Non-UUID values are silently ignored and the scope falls back to the SDK's default session ID — so a malformed or missing header from a client will never crash the request handler. Enable `debug: true` on `Pulse.configure()` to see warnings when invalid values are received.

### Cross-SDK Session Correlation

The typical use case is linking backend events to the session of the client that triggered them. Every client SDK exposes its current session ID as `Pulse.sessionId`; have the client send it as a request header, then scope the handler on the server.

Web client — the SDK adds the header for you on `fetch` requests to the origins you list:

```typescript
Pulse.configure({
  endpoint: "https://ingest.pulse.pubky.org",
  apiKey: "pulse_client_...",
  bundleId: "app.example.com",
  propagateSessionTo: ["https://api.example.com"],
});

// Automatically carries X-Pulse-Session-Id.
await fetch("https://api.example.com/checkout", { method: "POST" });
```

Only list origins you control — the header should not leak to third parties. Propagation works by wrapping `fetch`, so `XMLHttpRequest` and `sendBeacon` requests (axios in the browser defaults to XHR) are not annotated and must set the header themselves:

```typescript
const xhr = new XMLHttpRequest();
xhr.open("POST", "https://api.example.com/checkout");
if (Pulse.sessionId) xhr.setRequestHeader("X-Pulse-Session-Id", Pulse.sessionId);
```

Swift client:

```swift
var request = URLRequest(url: apiURL)
if let sessionId = Pulse.sessionId {
    request.setValue(sessionId, forHTTPHeaderField: "X-Pulse-Session-Id")
}
```

Node server (Fastify):

```typescript
app.addHook("onRequest", async (request) => {
  const clientSessionId = request.headers["x-pulse-session-id"] as string | undefined;
  const base = request.user?.id ? Pulse.withUser(request.user.id) : Pulse;
  request.pulse = clientSessionId ? base.withSession(clientSessionId) : base;
});
```

Every event emitted through `request.pulse` — plus any operations or funnel steps started from it — now shares the client's session ID, so the dashboard's session view shows both sides of the transaction together.

### Per-call override

For callers that can't scope (e.g. a utility that's handed a sessionId but not a ScopedPulse), `info/debug/warn/error` accept a `sessionId` in their options:

```typescript
Pulse.info("Webhook received", { provider: "stripe" }, { sessionId: clientSessionId });
```

When both a scope and a per-call `options.sessionId` are present, the per-call value wins.

## Anonymous vs Known Users

When no user ID is set (i.e., you use `Pulse` directly instead of `Pulse.withUser()`), events are emitted without a `user_id` field. They are still grouped by `session_id`, but cannot be attributed to a specific user.

For backend services that handle both authenticated and unauthenticated requests, the middleware pattern above handles this naturally -- unauthenticated requests fall through to the base `Pulse` instance.

## User Scoping with Operations

Operations started from a scoped instance carry the user ID across all lifecycle events (start, complete, fail, cancel):

```typescript
const pulse = Pulse.withUser(userId);
const op = pulse.startOperation("data-export");

try {
  const result = await exportUserData(userId);
  op.complete({ rows: String(result.rowCount) });
} catch (err) {
  op.fail(err.message);
}
```

Both the `start` and `complete` (or `fail`) events will have `user_id` set.

## User Scoping with Funnels

Funnel analytics correlate steps by user ID. Always use a scoped instance when tracking funnel steps:

```typescript
const pulse = Pulse.withUser(userId);
pulse.step("signup-started");
// ... later
pulse.step("email-verified");
pulse.step("first-project-created");
```

Without a user ID, the server cannot determine which user completed which steps. See the [Funnels guide](/docs/sdks/node/funnels) for more backend funnel patterns.
