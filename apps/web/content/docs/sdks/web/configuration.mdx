Use `Pulse.init()` early in the page lifecycle. These APIs require a package release containing
`init`, `captureException`, `ignoreErrors`, the route helper and origin URL mode; Web SDK 0.5.1 does
not include them. The source examples below target the release containing those changes.

## Basic Configuration

```typescript
import { Pulse } from "@synonymdev/pubky-pulse-web";

Pulse.init({
  apiKey: "pulse_client_...",
  appVersion: "1.4.0",
});
```

## Safe Optional Initialization

```typescript
const result = Pulse.init({
  apiKey: process.env.NEXT_PUBLIC_PULSE_KEY,
  enabled: process.env.NODE_ENV !== "test", // Keep deployment/test decisions app-owned.
});
```

`init` returns a frozen `{ status, reason }` diagnostic without exposing keys, endpoints or caught
exceptions. `status` is `enabled`, `disabled` or `error`. Inspect it when setup diagnostics are
needed; initialization failures do not throw into application startup.

| Reason | Meaning |
|---|---|
| `initialized` | A browser client started. |
| `unchanged` | Equivalent normalized options retain the existing session and collectors; hooks compare by reference. |
| `configuration-ignored` | A valid changed configuration was ignored: the first successful initialization wins. |
| `disabled` / `missing-key` | Explicit opt-out, or an absent/null/blank key. |
| `ssr` | No browser; a later browser initialization can still start. |
| `invalid-configuration` | Invalid options. A running valid client is preserved. |
| `initialization-failed` | Setup failed; installed resources were rolled back. |

Disabled or server-side initialization creates no identity or session, reads/writes no storage,
installs no timers/listeners/fetch wrapper, and makes no requests or offline replay. Missing and
whitespace-only keys disable tracking even without `enabled: false`. An explicitly invalid endpoint
never falls back to the hosted service.

`Pulse.init({ enabled: false })` also stops an active client. It discards fresh buffered telemetry
without flushing or persisting it, stops pending SDK work, and preserves pre-existing browser data.
Requests already sent cannot be recalled. A later enabled initialization may replay the old queue.
To change a running configuration while sending pending telemetry first, use `await Pulse.shutdown()`
then `init` again. To discard pending telemetry, disable before reinitializing.

`Pulse.configure()` remains available for existing consumers: it validates strictly and throws on
invalid options, including during SSR; valid repeated calls explicitly reconfigure the client.
`captureException` is a quiet no-op before initialization, when disabled and outside the browser.

## Event Resource Limits

The SDK limits each event to **128 KiB of serialized JSON**, its queued event buffer to **4 MiB**, and
its offline queue to a **1 MiB budget**, independently of event counts. A separate in-flight batch
can retain up to **2.5 MiB**; these payload limits are not a total heap cap. Oversized events are dropped
before attachment scheduling; the buffer drops oldest events to admit newer ones. At most 100 own
attributes are inspected, and keys over 256 UTF-16 code units are skipped. `beforeSend` continues to
receive full message and admitted attribute strings; string truncation and the event byte check
happen after it returns.

Offline admission accounts for the shared queue and unload spill keys. Unload cannot rewrite a
locked shared key, so fresh events can be dropped when that key fills the budget. The aggregate cap
is best effort across concurrent tabs; quota failures can also discard telemetry. Raising
`maxBufferSize` does not raise byte budgets. [Attachments](/docs/sdks/web/attachments#browser-resource-limits)
have separate, intentionally smaller browser limits.

## Options

| Option | Type | Default | Description |
|---|---|---|---|
| `endpoint` | `string` | `"https://ingest.pubkypulse.com"` | Pubky Pulse ingest server URL. A trailing slash is stripped. Omit it to use Pubky's hosted instance; self-hosters must set their own. |
| `apiKey` | `string` | — | Client key with `pulse_client_` prefix. Required by `configure`; absent/null/blank disables `init`. |
| `enabled` | `boolean` | `true` | `init` only: false disables tracking without flushing fresh telemetry. |
| `bundleId` | `string` | — | Deprecated compatibility option. Not needed: the client key identifies the app. Legacy servers may still require it until upgraded. |
| `appVersion` | `string` | `undefined` | Version reported with every event. Set it, and make it increase between releases — see [App version](#app-version). |
| `isDev` | `boolean` | `true` on `localhost`, `127.0.0.1`, or a `file:` URL | Marks events as development traffic. See [Data Mode](/docs/concepts/data-mode). |
| `debug` | `boolean` | `false` | Print the SDK's own diagnostics to the console. |
| `consoleLogging` | `boolean` | `true` | Mirror logged events to the console. |
| `compressionEnabled` | `boolean` | `true` | gzip request bodies where the browser supports it. |
| `captureUnhandled` | `boolean` | `true` | Capture uncaught errors and unhandled rejections. See [Events](/docs/sdks/web/events#unhandled-errors). |
| `trackPageViews` | `boolean` | `true` | Emit screen events for History API navigations. See [Screens](/docs/sdks/web/screens). |
| `screenNameForPath` | `(pathname: string) => string` | `undefined` | Map automatic routes to stable screen names. Must be a synchronous function. See [Mapping route names](/docs/sdks/web/screens#mapping-route-names). |
| `beforeSend` | `(event, hint) => LogEvent \| null` | — | Synchronous application redaction/filter hook; failures drop the event. See [Events](/docs/sdks/web/events#filtering-and-redaction). |
| `ignoreErrors` | `(string \| RegExp)[]` | `[]` | Filter exception and error logger messages before hooks and output. |
| `networkTracking` | `boolean \| { urlMode?: "path" \| "origin" }` | `false` | Emit fetch events; true or an empty object preserves sanitized paths. |
| `propagateSessionTo` | `string[]` | `[]` | URL prefixes whose `fetch` requests receive the `X-Pulse-Session-Id` header. |
| `flushIntervalMs` | `number` | `5000` | Milliseconds between automatic flushes. |
| `flushThreshold` | `number` | `20` | Buffered events that trigger an immediate flush. |
| `maxBufferSize` | `number` | `10000` | Buffered event count ceiling; the 4 MiB byte cap can drop oldest events sooner. |
| `sessionTimeoutMs` | `number` | `1800000` | Idle time (30 minutes) after which a new session starts. |
| `supportedLanguages` | `string[]` | *not sent* | The locales your app ships. Written through to the app record and used for localization-gap analysis. |

Client-key-only configuration needs a server that accepts events without `bundle_id`. Upgrade
self-hosted servers before omitting the existing `bundleId`; older clients that send it remain
compatible. The new capture/privacy APIs change no ingest schema.

Every numeric option must be a positive integer, and `flushThreshold` must not exceed `maxBufferSize`; invalid values throw at `configure()` time with a `Pubky Pulse: ...` message. `init()` returns an error diagnostic for invalid configuration.

<Callout>
Set `supportedLanguages` explicitly to the locales your app ships — `supportedLanguages: ["en", "es", "fr"]`. It is an app-level field, not a per-event label: the server writes the first value it sees in a batch through to the app record with source `sdk`, overriding anything set by hand. Leaving it unset sends nothing at all, so a manually configured list stays as it is. See [Ingest](/docs/api-reference/ingest).
</Callout>

## Allowed Origins

The client key you pass as `apiKey` is public: it ships inside the page, so anyone can read it out of the network tab. What scopes it to your sites is the app's **allowed origins** list — the browser origins the server accepts requests from for this app.

Set it on the app, not in the SDK and not in the server's environment:

- **Where** — the app's card in the dashboard, `PATCH /v1/apps/:id`, or the `update-app` MCP tool. One full origin per entry: scheme, host, optional port, no path and no trailing slash.
- **Include your dev server** — `http://localhost:5173`, `http://localhost:3000`, whatever you run locally. A missing dev origin is the usual reason nothing arrives while developing.
- **An empty list blocks every browser.** A newly created web app has no origins, and until it does, ingest answers `403` and CORS refuses the preflight.
- **`CORS_ORIGINS` is not this.** That server variable is the dashboard's own origin; you do not need a server change to add a site.

See [Allowed Origins](/docs/concepts/projects-and-apps#allowed-origins).

## App Version

`appVersion` is the only release identifier a browser app has — web events carry no build number — so leaving it unset costs you the version badges across the dashboard and disables [issue regression detection](/docs/concepts/issues#regression-detection) for this app entirely.

It also has to **increase** between releases. Versions compare segment by segment, numerically where a segment is numeric and as plain strings otherwise, so a git SHA or a content hash sorts alphabetically rather than chronologically and "latest" becomes whichever hash happens to sort highest.

```typescript
Pulse.init({
  // Explicit host: required when you run your own instance.
  endpoint: "https://ingest.yourdomain.com",
  apiKey: "pulse_client_...",
  // Injected at build time from package.json — not the commit SHA.
  appVersion: __APP_VERSION__,
});
```

`1.4.0`, `1.4.0-rc.2`, and `2026.04.23` all order correctly; `a3f9c21` and `main-2f4c9` do not. See [Latest Version Detection](/docs/concepts/latest-version-detection#web-apps-must-set-appversion).

## Page Context Attributes

`screen_name` defaults to the URL **path** — `/checkout/payment`, without the query string — and can use a mapped or manual name. Mapping changes only screen naming; it does not sanitize URL-bearing attributes. Two reserved `custom_attributes` keys can carry the full page URL and referrer, each capped at 2048 characters instead of the usual 200:

```typescript
Pulse.info("checkout_started", {
  _page_url: location.href,
  _referrer: document.referrer,
});
```

Reserved keys are underscore-prefixed and interpreted by the server, so use these two rather than inventing `page_url` of your own. Auto-instrumented `fetch` calls use the same mechanism, recording `_http_url`, `_http_method`, `_http_status`, and `_http_duration_ms` (status `"0"` when the request never completed). See [Custom Attributes](/docs/concepts/events#custom-attributes).

## What Happens on Enabled Initialization

1. **Checks opt-in and browser availability** — an absent key, explicit disable, or missing `window` returns a disabled result before browser setup.
2. **Validates** the endpoint, key format, and options. An existing client keeps its first successful configuration.
3. **Installs reversible page hooks** — page-visibility flushing, screen tracking when `trackPageViews` is on, unhandled-error capture when `captureUnhandled` is on, and the `fetch` wrapper when `networkTracking` or `propagateSessionTo` needs it. Setup failures roll these back before identity/session creation.
4. **Loads or creates the anonymous id** (`pulse_anon_<uuid>` in `localStorage`) so the first event already has a user id.
5. **Starts or resumes a session** — a UUID kept in `sessionStorage`. The stored id is adopted when the last activity is inside `sessionTimeoutMs`, so a reload in the same tab keeps the session and emits no session-start event; `sdk:session_started` is emitted only when a new session actually begins. The initial mapped screen is then recorded. See [Sessions](/docs/sdks/web/identity#sessions).

Repeated `init()` calls keep the active pipeline. Legacy `configure()` validates before checking for `window` and explicitly replaces the pipeline, draining the old transport and removing its page hooks.

## Development vs Production Data

`isDev` controls whether events are tagged as development or production data. It defaults to `true` on `localhost`, `127.0.0.1`, and `file:` URLs, so local work stays out of your production numbers without any extra setup. Override it when your staging domain should also count as dev:

```typescript
Pulse.init({
  apiKey: "pulse_client_...",
  isDev: location.hostname.endsWith(".staging.example.com"),
});
```

The [Data Mode](/docs/concepts/data-mode) filter in the dashboard and the `data_mode` argument on MCP query tools let you separate the two.

## Network Tracking and Session Propagation

```typescript
Pulse.init({
  apiKey: "pulse_client_...",
  networkTracking: { urlMode: "origin" },
  propagateSessionTo: ["https://api.example.com"],
});
```

`networkTracking` defaults to false. `true` or `{ urlMode: "path" }` retains paths while stripping
credentials, query and fragment. `{ urlMode: "origin" }` records only protocol/host/port for HTTP(S)
URLs, resolving relative URLs against the page; malformed and non-HTTP(S) inputs omit `_http_url`
rather than sending their raw value. The policy applies before hooks, console, buffering and
persistence, including failed fetches.

Available method, status and duration are reported in `sdk:network_request`: debug for 2xx/3xx, warn for
other responses, error with status `0` on rejection. SDK endpoint requests remain excluded. Request
URLs, bodies and response/rejection values are unchanged; headers change only for explicit session
propagation. Origin hostnames may themselves contain identifiers, so this is not a general PII
guarantee. App-specific redaction may still be needed. Removing paths also means
[network issues](/docs/concepts/issues#network-request-errors-split-by-endpoint) group more broadly.

`propagateSessionTo` lists URL prefixes that receive the `X-Pulse-Session-Id` header on `fetch` requests, and works whether or not `networkTracking` is on. Propagation is implemented by wrapping `fetch`, so requests made with `XMLHttpRequest` or `sendBeacon` — including libraries such as axios that default to XHR in the browser — are not annotated and must set the header themselves. Only list origins you control: the header should not leak to third parties. See [Next.js](/docs/sdks/web/nextjs) for the server side of that trace.

Metadata and propagation are best effort for inputs or host APIs the SDK cannot safely inspect.
Tracking alone leaves method getters to native request conversion, so `_http_method` can be absent.
Propagation preserves inherited/non-enumerable options and getter receivers without cloning Request
bodies or replacing abort signals. Receiving handlers must accept requests without the session header.

## Flush and Shutdown

Batches are sent every `flushIntervalMs`, or as soon as `flushThreshold` events are buffered. Both ends are available when you need them:

```typescript
await Pulse.flush();    // attempt events; attachment waiting has a deadline
await Pulse.shutdown(); // flush, then remove every page hook the SDK installed
```

When the page is hidden or unloaded the SDK flushes on its own with a `keepalive` request and parks whatever does not fit in an offline queue in `localStorage`, which is drained on the next page load. Events logged while the browser reports itself offline queue up rather than fail.

Attachment waits have a 120-second ceiling. Noncancelable work can retain its resource reservation
and remaining accepted background work can continue afterward; see
[Browser Resource Limits](/docs/sdks/web/attachments#browser-resource-limits).
