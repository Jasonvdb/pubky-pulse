Use `Pulse.step()` to emit named step completions that feed into [funnel analytics](/docs/concepts/funnels). Each call logs `step:<name>` at info level.

## Tracking Steps

```typescript
Pulse.step("onboarding_email");
Pulse.step("onboarding_verify", { attempt: "2" });
Pulse.step("onboarding_done");
```

Use the same names every time and the server can draw the drop-off between them. Step names are free-form and kept verbatim — unlike metric slugs, nothing is normalised — so a typo becomes its own step.

## Steps and Identity

Funnel analytics correlate steps by user id. In the browser every step already carries one: the anonymous id before sign-in, the real id after [`Pulse.setUser()`](/docs/sdks/web/identity). Because `setUser` claims the anonymous history server-side, steps taken before sign-up still belong to the same person afterwards — which is what makes a sign-up funnel measurable at all.

```typescript
Pulse.step("signup_started");        // anonymous
// ... the user creates an account
await Pulse.setUser(user.id);        // claims everything above
Pulse.step("signup_completed");
```

## Mixing Browser and Backend Steps

Some steps happen where the browser cannot see them — a webhook, a background job, a payment confirmation. Emit those from the [Node.js SDK](/docs/sdks/node/funnels) with the same step names and the same user id, and the funnel spans both sides.

## Defining Funnels

Steps recorded by the SDK are matched against funnel definitions on the server. Define your funnels in the dashboard or with the `create-funnel` MCP tool, using the step names you pass to `step()`; each step's `event_filter.step_name` must match the string you send.

See [Funnels](/docs/concepts/funnels) for details on how funnel definitions, analytics, and query modes work.
