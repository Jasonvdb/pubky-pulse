A Next.js app has two halves, and Pubky Pulse has an SDK for each: the Web SDK in the browser, the [Node.js SDK](/docs/sdks/node) in route handlers and server actions. Propagate the session id between them and both halves of a request line up in the dashboard's session view.

## Client Component

`Pulse.init()` is safe during SSR and with an absent key. Start it in a client effect; repeated
equivalent initialization keeps the same session. No browser/key/session guards or initialization
try/catch are needed. Keep test and deployment decisions in `enabled`; inspect the returned
[diagnostic status](/docs/sdks/web/configuration#safe-optional-initialization) when useful.

```tsx
// app/pulse-provider.tsx
"use client";

import { useEffect } from "react";
import { Pulse } from "@synonymdev/pubky-pulse-web";

export function PulseProvider({ userId }: { userId?: string }) {
  useEffect(() => {
    Pulse.init({
      endpoint: process.env.NEXT_PUBLIC_PULSE_ENDPOINT,
      apiKey: process.env.NEXT_PUBLIC_PULSE_KEY,
      enabled: process.env.NODE_ENV !== "test",
      propagateSessionTo: ["/api"],
    });
  }, []);

  useEffect(() => {
    if (userId) void Pulse.setUser(userId).catch(() => {}); // Identity telemetry is optional here.
  }, [userId]);

  return null;
}
```

Mount it once in the root layout, and keep that layout synchronous:

```tsx
// app/layout.tsx
import { PulseProvider } from "./pulse-provider";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <PulseProvider />
        {children}
      </body>
    </html>
  );
}
```

Both keys are `NEXT_PUBLIC_`, which is correct here: the client key is public and ingest-scoped by design. Never put an agent key (`pulse_agent_...`) in a `NEXT_PUBLIC_` variable.

Awaiting a session in the root layout to fill `userId` would run a per-request read on every route in the app and opt the whole tree out of static rendering. It is not needed: `Pulse.setUser()` is a client-side call and the claim is [idempotent](/docs/sdks/web/identity), so pass the id from the client-side session your app already has.

```tsx
// app/use-pulse-user.ts
"use client";

import { useEffect } from "react";
import { Pulse } from "@synonymdev/pubky-pulse-web";
import { useAuth } from "@/lib/auth";

export function usePulseUser() {
  const { user } = useAuth();

  useEffect(() => {
    if (user) void Pulse.setUser(user.id).catch(() => {});
  }, [user]);
}
```

If the id can only come from the server, render `<PulseProvider userId={...} />` from a nested layout that is already dynamic rather than from the root.

## Route Handlers

`propagateSessionTo: ["/api"]` adds an `X-Pulse-Session-Id` header to eligible `fetch` requests matching
the `/api` path boundary. Propagation is best effort; `XMLHttpRequest` and `sendBeacon` are not
annotated. Read the optional header in route handlers to join browser and server events:

```typescript
// app/api/checkout/route.ts
import { Pulse } from "@synonymdev/pubky-pulse-node";

export async function POST(req: Request) {
  const sessionId = req.headers.get("x-pulse-session-id");
  const scope = Pulse.withUser(await currentUserId());
  const log = sessionId ? scope.withSession(sessionId) : scope;

  log.info("checkout_started");
  return Response.json({ ok: true });
}
```

The guard keeps the snippet type-correct — `Headers.get()` returns `string | null` — and the Node SDK ignores a non-UUID value and falls back to its own session id, so a request from outside the browser never breaks the handler. See [`Pulse.withSession()`](/docs/sdks/node/identity#withsession) for the details.

Configure the Node SDK once, in a module your route handlers import — with its own app and its own `pulse_client_` key for a `backend`-platform app. The two SDKs report to different apps in the same project; the shared session id is what joins them.

## Route Tracking

The App Router navigates with the History API, so the Web SDK's automatic screen tracking follows route changes with no extra work. Name the things the URL does not describe — a modal, a step in a checkout — with `Pulse.trackScreen()`. See [Screens](/docs/sdks/web/screens).

## Server Components and Server Actions

Use the Node.js SDK for server components and server actions. The Web SDK's `init` returns a
disabled SSR result and `captureException` quietly does nothing on the server, so a shared browser
helper is safe to import but records no backend events. Shared helpers that must log on both sides
should accept a logger appropriate to the environment.
