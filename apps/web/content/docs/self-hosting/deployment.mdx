Production deployment with pm2, nginx, Cloudflare, and firewall. This guide assumes you have completed the [Installation](/docs/self-hosting/installation) and [Configuration](/docs/self-hosting/configuration) steps.

## pm2 process manager

Create the pm2 ecosystem file at `/opt/pubky-pulse/ecosystem.config.cjs`:

```javascript
module.exports = {
  apps: [
    {
      name: "pulse-api",
      script: "apps/server/dist/index.js",
      cwd: "/opt/pubky-pulse",
      max_memory_restart: "300M",
      env: {
        NODE_ENV: "production",
      },
    },
    {
      name: "pulse-web",
      script: "node_modules/.bin/next",
      args: "start",
      cwd: "/opt/pubky-pulse/apps/web",
      max_memory_restart: "300M",
      env: {
        NODE_ENV: "production",
        PORT: 3000,
      },
    },
  ],
};
```

The `max_memory_restart: "300M"` cap auto-restarts a service if it balloons — useful on a 1–2 GB VPS where a runaway process can starve PostgreSQL.

Start the services, persist them across reboots, and enable log rotation:

```bash
cd /opt/pubky-pulse
pm2 start ecosystem.config.cjs
pm2 save

# Rotate pm2 logs at 5 MB, keep 7 files, gzip compressed
pm2 install pm2-logrotate
pm2 set pm2-logrotate:max_size 5M
pm2 set pm2-logrotate:retain 7
pm2 set pm2-logrotate:compress true
```

Verify both services are running:

```bash
pm2 status
# pulse-api    online
# pulse-web    online
```

### Useful pm2 commands

```bash
pm2 logs pulse-api --lines 50    # View recent API server logs
pm2 logs pulse-web --lines 50    # View recent web dashboard logs
pm2 restart all                      # Restart both services
pm2 reload all                       # Zero-downtime reload
```

## nginx reverse proxy

Create the nginx config at `/etc/nginx/sites-available/pubky-pulse`:

```nginx
# API server (agent keys, dashboard API, auth, attachment uploads/downloads)
server {
    listen 80;
    server_name api.yourdomain.com;

    # Event attachments can be up to 250 MB per upload (per-user quota default)
    client_max_body_size 260m;

    location / {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }

    # Internal location for attachment downloads served via X-Accel-Redirect.
    # Full snippet: deploy/attachments-nginx-snippet.conf
    location /_attachments/ {
        internal;
        alias /opt/pubky-pulse-attachments/;
        types { }
        default_type application/octet-stream;
        add_header X-Content-Type-Options nosniff always;
        add_header Cache-Control "private, no-store" always;
        send_timeout 5m;
    }
}

# Ingest (SDK client keys)
server {
    listen 80;
    server_name ingest.yourdomain.com;

    client_max_body_size 2m;

    location / {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# Web dashboard
server {
    listen 80;
    server_name yourdomain.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

Enable and test:

```bash
ln -sf /etc/nginx/sites-available/pubky-pulse /etc/nginx/sites-enabled/pubky-pulse
rm -f /etc/nginx/sites-enabled/default
nginx -t
systemctl reload nginx
```

The ingest server block sets `client_max_body_size 2m` to allow compressed event batches. The API and web server blocks include WebSocket upgrade headers for potential future use.

### Attachments

The config above already includes the `/_attachments/` internal location and a 260 MB `client_max_body_size` to allow SDK attachment uploads. Downloads are served via nginx `X-Accel-Redirect`, which maps the internal URI prefix (`PULSE_ATTACHMENTS_INTERNAL_URI=/_attachments/`) to the on-disk directory (`PULSE_ATTACHMENTS_PATH=/opt/pubky-pulse-attachments`). The full reference snippet with comments lives at `deploy/attachments-nginx-snippet.conf` in the repo.

The directory must be writable by the user running pm2 (`root` in the default setup):

```bash
mkdir -p /opt/pubky-pulse-attachments
chown -R root:root /opt/pubky-pulse-attachments
```

## Cloudflare setup (recommended)

Using Cloudflare provides SSL termination, DDoS protection, and CDN caching.

### DNS records

Create three A records in Cloudflare, all pointing to your VPS public IP with **Proxy enabled** (orange cloud):

| Type | Name | Content | Proxy |
|------|------|---------|-------|
| A | `@` | VPS IP | Proxied |
| A | `api` | VPS IP | Proxied |
| A | `ingest` | VPS IP | Proxied |

### SSL settings

The nginx example above is HTTP-only. Cloudflare's **Full** and **Full (Strict)** modes connect to the origin over HTTPS on port 443, so neither mode works until origin TLS is configured. Do not use **Flexible** as a workaround: it leaves the edge-to-origin hop unencrypted and can create redirect loops.

The recommended setup is a Cloudflare Origin CA certificate covering the apex, `api`, and `ingest` hostnames. Save its certificate and private key on the server, restrict the private key, then replace `listen 80;` in each application server block above with these directives:

```nginx
listen 443 ssl http2;
ssl_certificate /etc/ssl/pubky-pulse/origin.pem;
ssl_certificate_key /etc/ssl/pubky-pulse/origin.key;
```

Add one separate HTTP redirect block:

```nginx
server {
    listen 80;
    server_name yourdomain.com api.yourdomain.com ingest.yourdomain.com;
    return 301 https://$host$request_uri;
}
```

Run `nginx -t` before reloading nginx, then set Cloudflare's encryption mode to **Full (Strict)**. A Cloudflare Origin CA or publicly trusted certificate supports Strict mode. If you deliberately use a self-signed origin certificate, use **Full** instead; never use Flexible.

## SSL without Cloudflare

If you are not using Cloudflare, use Let's Encrypt for free SSL certificates:

```bash
apt install -y certbot python3-certbot-nginx
certbot --nginx -d yourdomain.com -d api.yourdomain.com -d ingest.yourdomain.com
```

Certbot automatically modifies the nginx config to listen on port 443 and sets up auto-renewal.

## Firewall (UFW)

Lock down the VPS to accept SSH only from a VPN (Tailscale) and HTTP/HTTPS only from Cloudflare IP ranges:

```bash
ufw default deny incoming
ufw default allow outgoing

# SSH via Tailscale only
ufw allow in on tailscale0 to any port 22 proto tcp

# HTTP/HTTPS from Cloudflare IPs
for cidr in $(curl -s https://www.cloudflare.com/ips-v4/); do
  ufw allow from "$cidr" to any port 80,443 proto tcp
done
for cidr in $(curl -s https://www.cloudflare.com/ips-v6/); do
  ufw allow from "$cidr" to any port 80,443 proto tcp
done

ufw --force enable
```

If you are not using Cloudflare, replace the Cloudflare IP rules with:

```bash
ufw allow 80/tcp
ufw allow 443/tcp
```

## Deploying updates

Pull the latest code, rebuild, run migrations, and restart:

```bash
cd /opt/pubky-pulse
git pull
pnpm install
pnpm build
DATABASE_URL='postgresql://pubky_pulse:yourpassword@localhost:5432/pubky_pulse' pnpm db:migrate
pm2 restart all
```

The `DATABASE_URL` prefix is required for `pnpm db:migrate` because migrations run from `packages/db` and do not auto-load the root `.env` file.

## Verification

After deployment, verify that everything is working:

```bash
# Health check (local)
curl -s http://localhost:4000/health
# {"status":"ok"}

# Health check (external, via Cloudflare)
curl -s https://api.yourdomain.com/health
curl -s https://ingest.yourdomain.com/health
```

Open `https://yourdomain.com` in a browser to access the dashboard.

## Database maintenance

- **Partitions** are auto-created on server startup (current month plus 2 months ahead). No manual intervention required.
- **Auto-pruning** runs hourly when `MAX_DATABASE_SIZE_GB` is set. It drops the oldest monthly partitions first.
- **Per-project retention** is enforced by the `retention_cleanup` background job (daily at 2am UTC) using the `retention_days_events`, `retention_days_metrics`, and `retention_days_funnels` columns on `projects`.
- **Size check:** `psql -c "SELECT pg_size_pretty(pg_database_size('pubky_pulse'));"`

### Backups

Dump the Postgres database separately from attachment bytes under `PULSE_ATTACHMENTS_PATH`. Back up attachments with a filesystem or object-storage tool; `pg_dump` cannot include them.

Store the database password in `/root/.pgpass` rather than in the cron definition:

```bash
printf '%s\n' '127.0.0.1:5432:pubky_pulse:pubky_pulse:yourpassword' > /root/.pgpass
chmod 600 /root/.pgpass
```

Create the backup directory and `/usr/local/sbin/pubky-pulse-backup` with the following contents. The temporary file, `pipefail`, integrity checks, and delayed pruning prevent a failed `pg_dump` from replacing good backups or triggering retention cleanup:

```bash
#!/usr/bin/env bash
set -euo pipefail

backup_dir="/opt/pubky-pulse-backups"
backup_date="$(date -u +%F)"
temporary_file="$backup_dir/.pubky-pulse-$backup_date.sql.gz.tmp"
final_file="$backup_dir/pubky-pulse-$backup_date.sql.gz"

install -d -m 700 "$backup_dir"
trap 'rm -f "$temporary_file"' EXIT

pg_dump \
  --host=127.0.0.1 \
  --username=pubky_pulse \
  --dbname=pubky_pulse \
  --no-owner \
  | gzip -9 > "$temporary_file"

gzip -t "$temporary_file"
if [[ "$(stat -c %s "$temporary_file")" -lt 1024 ]]; then
  echo "Backup is unexpectedly small; refusing to publish it" >&2
  exit 1
fi

mv "$temporary_file" "$final_file"
trap - EXIT

find "$backup_dir" -maxdepth 1 -type f \
  -name 'pubky-pulse-*.sql.gz' -mtime +7 -delete
```

Make the script root-only, run it manually once, and verify the resulting archive before scheduling it:

```bash
chmod 700 /usr/local/sbin/pubky-pulse-backup
/usr/local/sbin/pubky-pulse-backup
gzip -t /opt/pubky-pulse-backups/pubky-pulse-$(date -u +%F).sql.gz
```

Schedule the verified script at 3am UTC with seven-day rotation handled inside the script:

```bash
# /etc/cron.d/pubky-pulse-backup
0 3 * * * root /usr/local/sbin/pubky-pulse-backup >> /opt/pubky-pulse-backups/backup.log 2>&1
```

### Health checks

A simple health-check cron auto-restarts a service if it stops responding. Runs every 5 minutes against the API `/health` endpoint and the web dashboard root:

```bash
# /etc/cron.d/pubky-pulse-healthcheck
*/5 * * * * root (curl -sf http://127.0.0.1:4000/health > /dev/null || pm2 restart pulse-api) >> /opt/pubky-pulse-backups/healthcheck.log 2>&1
*/5 * * * * root (curl -sf http://127.0.0.1:3000/ > /dev/null || pm2 restart pulse-web) >> /opt/pubky-pulse-backups/healthcheck.log 2>&1
```

The log file stays empty when both services respond. Entries appear only when a restart was triggered.

## Troubleshooting

```bash
# Check if services are running
pm2 status

# Check service logs for errors
pm2 logs pulse-api --lines 100

# Validate nginx config
nginx -t

# Test database connectivity
psql $DATABASE_URL -c "SELECT 1;"

# Check disk space
df -h

# Restart everything
pm2 restart all
systemctl reload nginx
```
